## 📁 Project Structure

The framework supports two configuration formats:

### New Format (v2.0) - Recommended
```
your-project/
├── minions.json              # Single config file (version controlled)
├── .minions/                 # Runtime state folder (gitignored)
│   ├── agents/               # Per-agent state files
│   │   └── {agent-id}.json   # Individual agent state
│   ├── base-agent.json       # Base branch agent state
│   ├── archive/              # Archived agent metadata
│   └── cache/                # Cached data
└── CLAUDE.md                 # Optional, generated by wizard
```

### Legacy Format (v1) - Still Supported
```
your-project/
├── minions/                  # Copied framework folder
│   ├── config.json           # Project configuration
│   ├── bin/                  # Shell scripts
│   ├── rules/                # Agent behavior rules
│   └── templates/            # Mission templates
├── .agent-info               # Runtime state (gitignored)
└── .minions-base-info        # Base agent state (gitignored)
```

## 🎯 Features Implemented

### 1. Data Model & Schema ✅
- Created `minions.json` configuration format (v2.0)
- Legacy `config.json` format still supported with automatic migration
- Defined TypeScript types in `gui/src/main/services/types/`
- Project-scoped state storage in `.minions/` directory
- Agent archiving for historical reference

### 2. Main Process Services ✅
- **ProjectService**: Manages project selection and recent projects
- **AgentService**: Discovers agents via git worktrees (git projects) or direct directory (non-git projects), manages missions, archiving
- **TerminalService**: Spawns node-pty sessions, tmux integration, signal detection
- **ClaudeSessionInfoService**: Parses Claude JSONL session files
- **MinionsConfigService**: Read/write minions.json, automatic format migration
- **SetupWizardService**: One-click project setup wizard using Claude
- **NotificationService**: OS-level notifications for agent signals
- **PRPollingService**: GitHub PR status polling and monitoring
- **SettingsService**: Application settings and preferences
- **WorkflowService**: Workflow orchestration and automation
- **TeleportService**: Agent teleportation functionality
- **TestEnvService**: Test environment management
- **IdleDetector**: Detects idle agents for automated actions

### 3. Terminal Integration ✅
- Full xterm.js terminal with node-pty backend
- Tmux integration for session persistence
- Interactive input/output
- ANSI color support
- Automatic resize handling
- Signal detection in output stream
- Multiple terminal tabs per agent
- Test environment terminals

### 4. Signal Protocol ✅
- Documented in `minions/rules/orchestrator_signals.md`
- Six signals: PLAN_READY, DEV_COMPLETED, BLOCKER, QUESTION, WORKING, PLANS_READY
- Automatic detection via ANSI stripping and pattern matching
- OS-level notifications for each signal type
- UI status badges and banners

### 5. UI Components ✅

#### Core Components
- **ProjectPicker**: Folder selection dialog, recent projects, project validation
- **Sidebar**: Agent list with status badges, Home navigation, running indicators
- **Dashboard**: Kanban-style columns, mission cards, agent creation modal
- **AgentView**: Terminal integration, tool/mode selectors, start/stop controls

#### Agent Management
- **SuperAgentView**: Super minion management and sub-agent coordination
- **PlanApproval**: Plan review and approval interface for super minions
- **AgentHeader**: Agent information and controls header

#### Settings & Configuration
- **SettingsPage**: Application settings and preferences
- **SetupWizard**: One-click project setup wizard

#### Terminal Components
- **Terminal**: xterm.js integration with bidirectional communication
- **TerminalTabs**: Multiple terminal tabs per agent
- **TestEnvTerminal**: Dedicated test environment terminals

#### Additional Components
- **QuickInput**: Quick input modal for agent prompts
- **StatusBadge**: Agent status indicators
- **NotificationBanner**: Signal notification display

### 6. IPC Bridge ✅
- Typed API between Main and Renderer
- Project operations
- Agent operations
- Terminal operations
- Assignment CRUD
- Event listeners for updates

### 7. Script Integration ✅
- Updated `setup.sh` to copy signal rules
- Migration script for ASSIGNMENTS.md → JSON
- Test signal script for validation

## 🎨 Design Decisions

### Why Electron?
- Cross-platform (macOS, Windows, Linux)
- Native access to file system and child processes
- Rich terminal integration
- Familiar web technologies

### Why node-pty?
- True PTY emulation (not just stdout/stderr)
- Handles interactive CLIs (claude, cursor)
- Preserves ANSI colors and control codes

### Why minions.json?
- Single configuration file at project root
- Easier to parse than Markdown tables
- Supports richer metadata (tool, model, mode)
- Better for programmatic updates
- Version controlled (unlike `.minions/` runtime state)
- Backward compatible with legacy format via automatic migration

### Why Project-Scoped State?
- Supports multiple projects on same machine
- Each project has independent agent state
- Clean separation of concerns

## 🐛 Known Limitations

1. **Terminal Persistence**: Tmux mode helps with session persistence, but sessions are cleaned up on app exit
2. **Cursor CLI**: Limited support (cursor doesn't have a well-documented CLI chat mode)
3. **Signal Detection**: Relies on agents following the protocol
4. **No Authentication**: Local-only app, no user accounts
5. **Single Window**: No multi-window support (multiple agents can be viewed via tabs)
