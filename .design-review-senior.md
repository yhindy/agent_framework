# Design Review: Customizable Workflow Editor

**Reviewer**: Senior Software Engineer
**Date**: 2026-01-13
**Status**: **APPROVE WITH CHANGES**

---

## Executive Summary

The engineering and UX design documents are well-structured and demonstrate good understanding of the existing codebase patterns. The workflow editor feature is technically sound and follows established Electron IPC patterns. However, several modifications are needed before implementation to ensure maintainability, prevent edge cases, and align with existing patterns.

---

## Technical Soundness Assessment

### Architecture: GOOD

The proposed architecture integrates cleanly with the existing system:

1. **Service Layer**: The new `WorkflowService` follows the established pattern of `AgentService`, `TerminalService`, etc.
2. **IPC Pattern**: The `workflow:*` namespace is consistent with existing patterns (`project:*`, `agents:*`, `assignments:*`).
3. **Data Storage**: Using JSON config files follows the existing pattern of `.agent-info` and `config.json`.

### Concerns

1. **Dual Type Definition**: The engineering doc defines types in `gui/src/main/services/types/WorkflowTypes.ts` while the UX doc defines them in `gui/src/renderer/src/components/WorkflowEditor/workflowTypes.ts`. This will cause drift. **Use a single source of truth.**

2. **Parallel Step Order Representation**: Using `order` field where multiple steps share the same order number is fragile:
   ```typescript
   // Current design - problematic
   { order: 2, executionMode: 'parallel' }  // step A
   { order: 2, executionMode: 'parallel' }  // step B
   ```
   This makes reordering complex and error-prone. Consider a nested structure instead.

3. **Rules Generation Integration Point**: The design mentions modifying `TerminalService.getClaudeArgs()` but this method doesn't exist. Review `TerminalService.startAgent()` for the actual integration point.

---

## Edge Cases and Missing Scenarios

### Critical Missing Cases

1. **Concurrent Edit Conflict**: No handling if user A opens workflow editor while user B modifies workflow config externally (via git pull, manual edit).

2. **Mid-Execution Workflow Changes**: What happens if a user modifies the workflow while a super minion is running? The design should:
   - Either lock the workflow during execution
   - Or explicitly state changes only apply to NEW executions

3. **Invalid Subagent Type Reference**: If `subagent-types.json` is updated to remove a type, existing workflows referencing that type will break. Need migration/validation on load.

4. **Empty Workflow Validation**: The testing strategy mentions `rejects empty workflows` but the data model allows `steps: []`. Should the UI prevent saving empty workflows, or warn?

5. **Circular Dependencies in Parallel Groups**: The design doesn't prevent putting a single step in a parallel group, which is semantically meaningless.

### Minor Missing Cases

- Maximum step limit not defined (what if user adds 50 steps?)
- Duplicate step names allowed? (UI clarity issue)
- Workflow template deletion not in IPC handlers

---

## Code Patterns Alignment

### Strengths

1. **IPC Handler Pattern**: Matches existing format perfectly:
   ```typescript
   ipcMain.handle('workflow:getConfig', async () => { ... })
   ```

2. **Preload Bridge Pattern**: Consistent with existing API exposure.

3. **Service Initialization**: Adding to `services!.workflow` follows existing pattern.

### Required Changes

1. **Preload Type Safety**: The design uses `any` in preload:
   ```typescript
   // Design proposes (BAD)
   saveProjectWorkflow: (projectPath: string, config: any) => ...

   // Should be (GOOD)
   saveProjectWorkflow: (projectPath: string, config: ProjectWorkflowConfig) => ...
   ```
   Update `gui/src/preload/index.d.ts` with proper types.

2. **Component Location**: New components should be in `gui/src/renderer/src/components/WorkflowEditor/` but the index barrel export pattern isn't used elsewhere in this codebase. Follow existing flat structure or document the new pattern.

3. **CSS File Organization**: The existing codebase uses component-specific CSS files (`SuperAgentView.css`, `AgentView.css`). The design's `WorkflowPanel.css` follows this pattern correctly.

4. **Test File Location**: Tests should be in `gui/src/main/services/__tests__/WorkflowService.test.ts` matching existing pattern.

---

## Performance Concerns

### Potential Issues

1. **Rules Generation on Every Start**: The design suggests generating rules markdown at runtime. For workflows with many steps, this could add latency to agent startup. Consider:
   - Caching generated rules until workflow changes
   - Pre-generating rules on workflow save

2. **Drag-and-Drop Performance**: With many steps (15+), drag-and-drop reordering without virtualization could cause jank. The design mentions "virtualize step list if needed" - recommend making this Phase 1 if step count exceeds 10.

3. **File Watcher Not Mentioned**: If project-level `workflow-config.json` is modified externally, the UI won't reflect changes. Consider a file watcher or manual refresh mechanism.

### Acceptable Performance Trade-offs

- Slide-out panel animation (480px width) is reasonable
- Debounced save on UI state changes follows existing pattern

---

## Security Assessment

### No Critical Issues

The design doesn't introduce security vulnerabilities:

1. Config files are project-local (no arbitrary file access)
2. No new IPC channels that could be exploited
3. Workflow prompts are user-controlled, same as existing assignment prompts

### Minor Recommendations

1. **Template Storage**: If templates are stored globally (not per-project), ensure path traversal isn't possible in template names.

2. **JSON Parsing**: Use try/catch around all JSON.parse calls for config loading (the test strategy mentions this).

## UX Design Feasibility

### Implementation Feasibility: HIGH

1. **Slide-Out Panel**: Straightforward React component with CSS transitions. No complex dependencies.

2. **Drag-and-Drop**: Recommend using a library like `@dnd-kit/core` rather than custom implementation. The design's up/down buttons as fallback is good for accessibility.

3. **Pipeline Visualization**: CSS connectors and markers are achievable. The animated gradient connector is a nice touch but should be optional (for accessibility/reduced motion preferences).

### Concerns

1. **"Configure Workflow" Button Location**: The design says "before the Make PR button" in `AgentHeader`. However, `AgentHeader` is shared between `AgentView` and `SuperAgentView`. The button should only appear for Super Minions. Verify this is handled via props.

2. **480px Fixed Width**: On smaller screens (1280px laptop), 480px takes significant space. Consider:
   - Responsive width (max 40% viewport)
   - Or full-screen modal on small viewports

3. **Keyboard Navigation**: The design mentions keyboard shortcuts but doesn't specify how they integrate with existing app shortcuts (see `KeyboardShortcutsHelp.tsx`). Ensure no conflicts with existing `Cmd+G`, etc.

### Missing UX States

1. **Loading State**: When workflow config is being fetched, what does the panel show?
2. **Save Failure State**: What happens if save fails? (Network error, permission issue)
3. **Validation Error State**: If workflow is invalid, how are errors displayed?
4. **Undo/Redo**: Not mentioned, but would be valuable for complex workflows

## Required Changes Before Implementation

### Must Fix (Blocking)

1. **Consolidate Type Definitions**: Use only `gui/src/main/services/types/WorkflowTypes.ts`. Import in renderer via IPC type bridge.

2. **Revise Parallel Step Representation**: Change from shared `order` number to explicit grouping:
   ```typescript
   interface WorkflowStep {
     id: string
     name: string
     subagentTypeId: string
     enabled: boolean
     config?: { ... }
   }

   interface ParallelGroup {
     type: 'parallel'
     steps: WorkflowStep[]
   }

   interface WorkflowConfig {
     items: (WorkflowStep | ParallelGroup)[]  // Ordered array
     // ... other fields
   }
   ```
   This matches the UX design's `WorkflowItem` type and is cleaner to manipulate.

3. **Add Workflow Locking for Running Agents**: Include `isLocked: boolean` or `lockedBy: string` in config to prevent edits during execution.

4. **Type Preload Bridge Properly**: No `any` types in the preload bridge.

### Should Fix (Recommended)

5. **Add Loading/Error States to UX Design**: Include mockups for loading, error, and validation states.

6. **Verify TerminalService Integration Point**: The method `getClaudeArgs()` doesn't exist. Clarify the actual integration in Phase 4.

7. **Add Step Count Limit**: Define maximum steps (e.g., 20) to prevent performance issues.

8. **Document Keyboard Shortcut Conflicts**: Audit existing shortcuts before assigning `Cmd+G` for grouping.
